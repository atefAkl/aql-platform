# SHARED ENVIRONMENT DEPLOYMENT PROCEDURE

**Project:** AQL Platform\
**Environment:** Shared Environment\
**Domain:** `platform.mawthiq.tech`\
**Branch:** `develop`\
**Status:** Draft 0.1

## 1. Purpose

Define the official path for moving an approved change from developer
local environments to the AQL Platform Shared Environment. The procedure
must be repeatable, deterministic, traceable, fail-fast, and safe.
Deployment to Shared Environment is not a Public Release.

## 2. Scope

Covers application source, PHP dependencies, frontend build artifacts,
database migrations, Laravel runtime preparation, verification, failure
handling, deployment records, and future automation. Production release
from `main` is outside this procedure.

## 3. Branch Model

``` text
Feature / Fix / Debug
        |
        v
Pull Request
        |
        v
Tech Lead Review
        |
        v
develop
        |
        v
Shared Environment
```

The Shared Environment follows `develop`. Feature branches must not
deploy directly.

## 4. Deployment Inputs

### 4.1 Application Source

The source code identified by the target Git commit.

### 4.2 PHP Dependencies

Dependencies are defined by `composer.lock`. Shared Environment uses
`composer install --no-dev --optimize-autoloader`, not
`composer update`.

### 4.3 Frontend Build Artifact

`public/build/` is generated by `npm run build` outside the Shared Host.
`public/build/` remains excluded from Git. The Shared Host is a Runtime
Environment, not the frontend Build Environment.

### 4.4 Database Changes

Schema changes are delivered through Laravel migrations. The Shared
Environment database is persistent; normal deployment must not run
destructive reset commands such as `migrate:fresh`.

## 5. Deployment Trigger

The official trigger is a successful merge into `develop`. Local changes
and feature branches do not directly deploy to Shared Environment.

## 6. Deployment Identity

Every deployment is identified by a Git commit SHA. Source code,
frontend artifact, and deployment record must correspond to the same
commit.

## 7. Deployment Status

`PENDING -> BUILDING -> READY -> DEPLOYING -> VERIFYING -> DEPLOYED`;
critical failure results in `FAILED`.

## 8. Deployment Sequence

1.  Identify target commit.
2.  Update application source.
3.  Install PHP dependencies.
4.  Deploy frontend build artifact.
5.  Apply database migrations.
6.  Clear/rebuild required Laravel caches.
7.  Verify application.
8.  Record deployment result.

Exact automation commands remain an implementation concern and are not
silently assumed by this procedure.

## 9. Source Deployment

Shared repository: `/home/agstores/repositories/aql-platform`; target
branch: `develop`. Deployment must correspond to the intended commit and
must never silently include local uncommitted changes.

## 10. PHP Dependency Deployment

Use the committed lock file and
`composer install --no-dev --optimize-autoloader`. Do not run
`composer update` on Shared Environment.

## 11. Frontend Artifact Deployment

Current validated model:

``` text
Build Environment -> npm ci -> npm run build -> public/build/ -> Shared Environment
```

Do not deploy `node_modules/`. Do not use `npm install` or
`npm run build` on the Shared Host as the frontend deployment mechanism.
The artifact must come from the same commit as the deployed source.

## 12. Database Migration Policy

Migrations are part of deployment. The automated process may use
`php artisan migrate --force` when appropriate. It must never perform
automatic destructive resets. Code rollback does not imply database
rollback. Migration rollback must be explicitly designed and validated.

## 13. Laravel Runtime Preparation

After source, dependencies, assets, and database changes, prepare
Laravel runtime and ensure stale configuration, route, view, or
application caches do not cause obsolete behavior. Exact cache commands
are finalized during automation design.

## 14. Verification

Verify domain/HTTPS, Laravel response, database connectivity and
migrations, Vite manifest and assets, authentication/session/CSRF, and a
minimum smoke test such as `GET /`, `GET /login`, `POST /login`, and
Platform Dashboard.

## 15. Failure Handling

A critical failure makes the deployment `FAILED`. The process must not
silently continue. Failure evidence must identify the stage and target
commit.

## 16. Rollback Boundaries

Source code, frontend artifact, PHP dependencies, database schema, and
runtime cache do not necessarily share the same rollback mechanism.
Never assume that restoring a previous Git commit safely rolls back the
database.

## 17. Deployment Record

Record at minimum: Deployment ID, Commit SHA, source branch, start/end
time, status, build result, dependency result, migration result,
verification result, and failure information where applicable.

## 18. Security

Keep `.env` outside Git. Never expose database passwords, private keys,
or other secrets in logs or source control. Use controlled deployment
credentials with the minimum required scope.

## 19. Current Manual Baseline

The real Shared Environment has been manually verified through: local
`develop` -\> local `npm run build` -\> `public/build/` -\> SCP -\>
Shared Host -\> Laravel -\> PostgreSQL -\> browser. PHP 8.3.33, Composer
2.8.12, Laravel 13.31.0, PostgreSQL connectivity, migrations, domain
routing, required directory traversal permissions, frontend assets,
login, and initial admin seeding have been verified.

This manual baseline is evidence for automation, not the intended
long-term deployment mechanism.

## 20. Future Automation Requirements

The automated flow should be:

``` text
GitHub merge to develop
        |
        v
CI / Build Environment
        |
        +-- checkout exact commit
        +-- validate
        +-- npm ci
        +-- npm run build
        +-- create deployment artifact
        |
        v
Deployment
        |
        +-- source
        +-- frontend artifact
        +-- Composer dependencies
        +-- migrations
        +-- runtime preparation
        +-- smoke test
        |
        v
Deployment Result
```

The exact division of responsibility between GitHub Actions/CI, cPanel
Git Deployment, SSH, and host deployment hooks must be determined from
the actual hosting capabilities.

## 21. Automation Principles

1.  Deploy only from `develop`.
2.  Deploy an identified commit.
3.  Build frontend assets from the same commit.
4.  Keep build and runtime environments separate.
5.  Fail fast on critical errors.
6.  Preserve deployment evidence.
7.  Avoid destructive database operations.
8.  Keep secrets outside Git.
9.  Make deployment repeatable.
10. Avoid dependence on a specific developer workstation.
11. Preserve the persistent Shared Environment.
12. Keep Shared Environment deployment distinct from Production release.

## 22. Document Relationship

``` text
Architecture Decisions
        |
        v
Architecture
        |
        v
Platform Contract

        v
Roadmap / Sprint Contract
```

If automation exposes a conflict with an approved architectural decision
or contract, the conflict must be surfaced and resolved before changing

## 23. Approval Gate

This document is Draft 0.1. Approval establishes the deployment behavior
and boundaries that automation must implement. After approval: inspect
actual cPanel deployment capabilities, choose the automation
architecture, implement it, test it, and document evidence.
